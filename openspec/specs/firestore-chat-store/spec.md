# firestore-chat-store Specification

## Purpose

ユーザー別の会話、run、順序付きイベントを永続化し、長時間実行中の応答をリアルタイムに購読するとともに過去セッションを再訪できる契約を提供する。

## Requirements

### Requirement: ユーザーとセッションを分離する
システムはすべてのセッション、run、イベントをユーザー ID の名前空間へ格納し、要求ユーザーが所有しないデータを取得、購読、更新してはならない（MUST NOT）。外部識別子を未検証のドキュメントパスとして使用してはならない（MUST NOT）。

#### Scenario: 他ユーザーのセッションを指定する
- **WHEN** 利用者が別ユーザーに属するセッション ID を指定する
- **THEN** システムは存在の詳細を漏らさずアクセスを拒否する

### Requirement: セッションを作成して一覧取得する
システムはユーザー別にセッションを作成し、更新日時の降順で安定したページングを行う一覧を返さなければならない（SHALL）。各項目にはセッション ID、表示用タイトル、作成日時、更新日時、最新 run の状態を含めなければならない（SHALL）。

#### Scenario: 過去セッションを一覧表示する
- **WHEN** 利用者が自分のセッション一覧を要求する
- **THEN** システムは当該ユーザーのセッションだけを更新日時の新しい順で返す

#### Scenario: 次ページを取得する
- **WHEN** 利用者が前ページで返されたカーソルを指定する
- **THEN** システムは重複や欠落を生じない安定した並びで次ページと次カーソルを返す

### Requirement: run要求を原子的に登録する
システムはユーザーメッセージ、run レコード、セッションの active run 参照を原子的に登録し、1 セッションに複数の active run を許可してはならない（MUST NOT）。同じ冪等キーの再送では既存 run を返さなければならない（SHALL）。

#### Scenario: 新しいrunを登録する
- **WHEN** active run のないセッションへ有効なメッセージと冪等キーを送る
- **THEN** システムはメッセージと新しい run を登録し、その run をセッションの active run とする

#### Scenario: active runが存在する
- **WHEN** active run のあるセッションへ別の run を登録しようとする
- **THEN** システムは既存 run の識別子と状態を返して新規登録を拒否する

### Requirement: runイベントを順序付きで追記する
システムは各イベントへ一意な event ID、run 内で単調増加する sequence、種別、発生時刻、payload を付けて追記しなければならない（SHALL）。同じ event ID の再送は重複イベントを作成してはならない（MUST NOT）。

#### Scenario: 複数イベントを保存する
- **WHEN** ジョブが応答、ツール利用、進捗、終端イベントを生成する
- **THEN** システムは run 内の確定した sequence 順でイベントを取得できるよう保存する

#### Scenario: イベント追記を再試行する
- **WHEN** 一時障害後に同じ event ID の追記が再送される
- **THEN** システムは既存イベントを返し、同じ論理イベントを二重表示させない

### Requirement: イベントをリアルタイム購読する
システムはセッションまたは run のイベントをリアルタイム購読でき、購読開始時のカーソルより後のイベントを順序付きで通知しなければならない（SHALL）。再配信が発生してもクライアントが event ID と sequence で重複を除ける情報を返さなければならない（SHALL）。

#### Scenario: 実行中の応答を受信する
- **WHEN** UI が run を購読中にジョブが新しいエージェントイベントを保存する
- **THEN** UI は定期的な全件ポーリングを行わず新しいイベントを増分受信できる

#### Scenario: 切断後に再購読する
- **WHEN** UI が最後に確認したカーソルを指定して購読を再開する
- **THEN** システムはそのカーソルより後の永続化済みイベントと以後の新規イベントを通知する

### Requirement: runの終端状態を整合して保存する
システムは completed、failed、cancelled、timed_out の終端状態、最終結果または安全なエラー、実行参照、snapshot 参照を run レコードへ保存しなければならない（SHALL）。completed は有効な snapshot commit と最終応答が保存された後にだけ設定しなければならない（SHALL）。

#### Scenario: 正常完了を保存する
- **WHEN** エージェント実行と snapshot 保存が成功する
- **THEN** システムは snapshot 参照と最終応答を保存した後に run を completed とし、セッションの active run を解除する

#### Scenario: 後続runが失敗する
- **WHEN** 直近の成功 run を持つセッションで後続 run が failed、cancelled、timed_out、または dispatch_failed になる
- **THEN** システムは active run を解除して当該 run の終端状態を保存するが、セッションの直近成功済み Claude セッション ID と snapshot 参照を消去または失敗 run の空値で上書きしてはならない

### Requirement: ストア実装を交換できる
セッション、run、イベントの操作は Firestore 固有型を公開契約へ漏らさず、同じ整合性、ページング、購読契約を満たす別ストア実装へ交換できなければならない（SHALL）。

#### Scenario: テスト用ストアへ差し替える
- **WHEN** 利用者がインメモリ実装を構成する
- **THEN** 制御クライアントとジョブライフサイクルは Firestore 接続なしで同じ公開操作を実行できる
