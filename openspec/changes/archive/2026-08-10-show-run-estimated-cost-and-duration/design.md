## Context

動機は [proposal.md](./proposal.md) を参照する。現在のClaude Agent adapterはResultMessageから最終出力だけを`final`または`error`イベントのpayloadへ移し、Job runnerはそのイベントをFirestore互換のChatEventとして逐次保存する。共通チャット層はpayloadを保持したままStreamlitとSlack Botへ渡すため、既存のイベント経路を拡張すれば追加の永続モデルやストアAPIを導入せずに両フロントエンドへ届けられる。

Claude Agent SDKの`total_cost_usd`は、その`query()`に含まれるモデル呼び出し、サブエージェント、およびSDKが認識するWeb Search等を集計したクライアント側の推定値である。`duration_ms`はSDKのquery処理時間であり、Cloud Runのキュー待ち、workspace復元、snapshot保存などrun全体の経過時間ではない。どちらもエラー経路では欠ける可能性がある。

## Goals / Non-Goals

**Goals:**

- 1回のrunに対応するSDK推定総費用とSDK処理時間を、最終結果と同じ永続イベントから一意に取得できるようにする。
- 新着ストリームと保存済み履歴で同じ値を扱い、StreamlitとSlack Botで同じ表示規則を使う。
- SDKの欠損値、古いイベント、および失敗結果に対して後方互換に動作する。

**Non-Goals:**

- トークン数、モデル別内訳、`duration_api_ms`、Web Search回数またはWeb Search費用だけの内訳は保存・表示しない。
- アプリケーション独自のモデル価格表やWeb Search単価表を管理しない。
- Google Cloud Billingの正式請求額との照合、通貨換算、ユーザーへの請求機能は提供しない。
- Cloud Runの待機時間を含むrun全体のwall-clock時間は計測しない。

## Decisions

### 1. ResultMessageの値を終端イベントpayloadへ追加する

adapterが生成する`final`および`error`イベントへ、次の任意フィールドを追加する。

- `estimated_cost_usd`: `total_cost_usd`から取得した有限な0以上の数値
- `duration_ms`: `duration_ms`から取得した0以上の整数

最終出力とメタデータを同じイベントに置くことで、イベント順序や別レコード間の結合に依存せず、runとの対応を維持する。Job runnerの正常完了時は既存のSDK由来finalイベントを再利用し、そのpayloadを縮退させない。SDK由来finalイベントが存在しない互換経路では、従来どおり出力だけのfinalイベントを生成する。

代案としてRunモデルへ列を追加する方法は、終端commitとイベント保存の二重書きになり、Firestore codecと全Store実装の変更範囲が増えるため採用しない。独立したmetricsイベントも最終結果との対応付けと終端競合が複雑になるため採用しない。

### 2. SDK推定総費用を再計算せず採用する

Web Search費用を含む処理全体の価格には`total_cost_usd`をそのまま使う。独自の単価表を重ねると、SDK側ですでに加算された検索費用の二重計上、価格改定への追従遅れ、Vertex AIの請求条件との差異が生じるためである。

この値は正式請求ではないため、永続キーと画面ラベルの両方で「推定」と明示する。SDKが価格を算定できず`None`を返す場合は、その事実を維持してフィールドを省略する。

### 3. 共通チャット層で安全に解釈・整形する

共通イベント層に、終端payloadから有効な`estimated_cost_usd`と`duration_ms`だけを取り出す小さな値表現と表示整形を置く。Pythonの`bool`、負数、NaN、Infinity、文字列は数値として受け付けない。これにより両フロントエンドで欠損判定、丸め、ラベルが分岐しない。

表示は費用を`推定価格 (USD): $0.012345`のように小額を失いにくい小数6桁、時間を`処理時間 (SDK): 12.34秒`のように秒へ換算した小数2桁とする。片方だけ有効なら有効な項目だけを返し、両方なければメタデータ行自体を生成しない。保存値は丸めず、丸めるのは表示時だけとする。

代案として各フロントエンドでpayloadを直接解釈する方法は、表示差異と入力検証漏れを生むため採用しない。

### 4. Streamlitでは各終端結果の直下に表示する

Streamlitの履歴描画では、`final`イベントの回答本文と同じassistant領域内にメタデータをcaptionとして表示する。これにより複数runを含む再訪セッションでも、どの処理に対する値かが崩れない。`error`イベントに値がある場合は成功回答として描画せず、安全な失敗表示の近くにメタデータだけを表示する。

### 5. Slack Botでは最終結果または失敗状態へ付記する

Slack Botはストリーム中の`final`または`error`イベントから処理メタデータを保持し、成功時は同一スレッドへ投稿する最終結果へ付記する。ストリーム境界で履歴フォールバックを行う場合も、本文と同時にメタデータを復元する。失敗時は成功の「最終結果」を作らず、終端状態を示す更新へ取得済みメタデータを付記する。

Slackの文字数制限に対しては既存の分割処理を通し、メタデータを含む本文も安全に分割する。

## Risks / Trade-offs

- [SDK推定額とGoogle Cloudの請求額がずれる] → 画面とフィールド名で推定値と明示し、正式な請求用途には使わないことをドキュメントとテストで固定する。
- [SDKのバージョンやエラー経路により値が欠ける] → 任意フィールドとして扱い、0へ補完せず従来の最終結果表示を継続する。
- [ユーザーが処理時間をrun全体の所要時間と誤解する] → `処理時間 (SDK)`と表示し、SDK外のキュー・復元・保存時間を含まないことを説明する。
- [非常に小さい費用が丸めで0に見える] → USDを小数6桁で表示し、元の数値は丸めず保存する。
- [将来payloadへ異なる型が混入する] → 共通層で有限・非負・非boolの値だけを表示対象にする。

## Migration Plan

1. adapterと共通イベント層を先に更新し、任意フィールドを生成・解釈できるようにする。
2. StreamlitとSlack Botの表示を更新し、SDK結果、保存済み履歴、失敗・欠損ケースのテストを追加する。
3. 既存のユニットテストとフロントエンドテストを実行した後に通常リリースする。Firestoreのスキーマ移行や既存データのbackfillは不要である。

ロールバック時は旧コードが追加payloadを透過的に保持または無視できるため、アプリケーションを前バージョンへ戻す。新形式イベントを削除・変換する必要はない。
